# Roadmap data and release history

The public roadmap is generated by `scripts/build-site-info.js` and `scripts/build-roadmap-page.js`. Never edit the built `dist/stipra/roadmap/index.html` or its `history.json` manually.

## Source files

- `docs/data/product-history.json` — public capability IDs, implementation state, acceptance state, initiatives and **published** versions.
- `docs/data/changelog.json` — dated development changes. A merged change is not automatically a release.
- `docs/data/delivery-ledger.json` — granular technical tracking, issue relationships and existing version/acceptance evidence. Remains the engineering source; not every issue should become a public capability.

When shipping code, update affected capability records in the same PR; keep IDs stable even if the wording, grouping, or priority changes. Add a new capability only for a real, independently testable behavior. Never compute a feature completion percentage from unweighted task counts.

Implementation values: `implemented`, `in-progress`, `planned`. Acceptance values: `digital-evidence`, `pending`, `not-evaluated`. These **do not imply distribution**. The `releases` collection is the only evidence of an official version.

## Release publication

The GitHub workflow `.github/workflows/release-history.yml` listens for an actual `release.published` event. It calls `scripts/sync-release-history.js`, which appends the tag, original publication timestamp, canonical release URL and title. Existing publication records cannot be rewritten by replaying a different event.

For precise capability-to-release mapping, include a line in the published GitHub release notes:

```
Capabilities: INK-01, OUT-02, LIB-03
```

The updater validates each ID. Without this line, it attempts a limited mapping from issue references (`#123`) in release notes. When no mapping exists, the release is still recorded, but its mapping is explicitly empty; never claim an unlisted feature shipped. The original dated changelog remains separate, preserving development history rather than reassigning all older changes to the latest release.

This automation needs `contents: write` on the default branch. Protected-branch restrictions can block the automatic commit; if that happens, use a reviewed PR for the generated history update. No public release is inferred from the owner-reported v0.8.0 working build.

## Verification

```sh
node --test tests/roadmap-history.test.js tests/site-info.test.js
npm run build:pages
```

Check `dist/stipra/roadmap/` at 320px, 390px and 1440px, keyboard focus/expansion, 200% zoom, and a real screen reader before treating the new presentation as accessibility-approved. Publish/build tests do not substitute for real print quality or artist acceptance.
